# Ajackus event assignment

Rails 8.1 / PostgreSQL app for importing Billetto public events and recording authenticated event votes.

## Setup

Requirements: Ruby 4.0.2, PostgreSQL, and Bundler.

```sh
bundle install
bin/rails db:prepare
bin/rails server
```

The event list is available at `/` (HTML) and `/events.json`. A vote is submitted with `POST /events/:event_id/vote.json` and JSON `{ "value": "up" }` or `{ "value": "down" }`. The vote endpoint accepts a Clerk session token in the `__session` cookie or as a Bearer token.

## Configuration

Set `BILLETTO_API_KEYPAIR` to a server-side Billetto API key pair, then run `bin/rails events:sync` to populate the local event list. `BILLETTO_API_URL` optionally overrides the API base URL (defaults to `https://api.billetto.com`). Production's Solid Queue recurring schedule also enqueues it every 30 minutes. The integration reads the paginated public `/events` endpoint and sends credentials only in the `Api-Keypair` request header.

Set `CLERK_JWT_KEY` to the Clerk PEM public verification key, `CLERK_ISSUER` to the Clerk instance issuer, and `CLERK_AUTHORIZED_PARTIES` to a comma-separated list of allowed app origins. The session verifier accepts RS256 Clerk session JWTs and checks signature, expiry, issuer, and authorized party. Configure these values in production. Sign-up, sign-in, and sign-out UI can be provided by Clerk's frontend SDK; this Rails app owns token verification and vote authorization.

## Design notes

- `Billetto::Client` handles HTTP, pagination, timeouts, and API errors. `Billetto::EventIngestor` validates and normalizes provider data, then upserts by external ID in page sized transactions. Database uniqueness protects idempotency when syncs overlap.
- `Billetto::EventSyncJob` runs provider work outside web requests. The production recurring schedule provides periodic reconciliation; the sync can also be run manually.
- The controller submits an `Events::CastVote` command through Arkency's command bus. Its handler publishes `Events::Upvoted` or `Events::Downvoted` into the event stream and links each fact to a user stream. Facts also contain the Clerk subject for traceability. The RES subscriber maintains one current vote per user and event; changing a vote appends another fact and updates the projection. The event row lock serializes concurrent changes to one event, while the unique database index is the final integrity guard.
- Rails Event Store uses PostgreSQL JSONB storage. Its table migration was generated by the gem. The vote projection handler runs synchronously in the publish transaction to keep the displayed totals consistent with accepted votes. Side effects that call other systems should use an after-commit asynchronous handler and an outbox if delivery must be guaranteed.
- Event list vote totals are loaded with one grouped query rather than one query per event.

## Verification

Run `bundle exec rspec`. Specs cover event validations, idempotent ingestion, vote event persistence/projection, invalid votes, and Clerk-protected voting.
